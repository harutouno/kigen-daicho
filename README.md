# 期限台帳

設備工事の会社で、**安全書類が差し戻される原因を、提出する前に洗い出す**ための台帳です。
社員の資格・講習・健診の期限と、道具・機器の点検・校正の期日を、同じ仕組みで扱います。

Python + Streamlit。外部サービスへの接続はありません。

---

## 1. なぜ作ったか

建設・設備の現場では、安全書類（グリーンファイル）の差し戻し原因として
**資格証の期限切れ**と**健康診断日の年度跨ぎ**が挙げられます。

どちらも「書類を作った日」ではなく、**提出する日や工期の終わりの時点**で
切れているために起きます。作成時点で有効かどうかを見ても防げません。

そこでこの台帳は、判定を「今日」に固定しません。
すべての判定関数が基準日を引数で受け取り、既定値を持ちません。
呼び出す側は、いつ時点の話をしているのかを必ず明示することになります。

```python
submission_check(ledger, target_date=date(2027, 3, 31))   # 工期末で判定
assignment_check(ledger, subject_id="p-001", ..., as_of=date(2026, 10, 1))
```

同梱データで実際に試すと、次のようになります。

| 提出日 | 引っかかる件数 | うち今日はまだ有効 |
|---|---|---|
| 今日 | 12件 | 0件 |
| 1か月半後 | 27件 | 15件 |
| 1年後（工期末） | 117件 | 105件 |

この表は `python -m data.stats` が同梱データから計算した値です。手では書きません。
`tests/test_readme.py` が README と計算結果を突き合わせるので、ずれると pytest が落ちます。

今日の画面では76人中65人が「問題なし」ですが、1年の工期で見ると
年1回の健康診断がほぼ全員分失効します。
**社員の一覧を眺めているだけでは気づけません。**

## 2. 画面

| 画面 | 内容 |
|---|---|
| 社員の資格・健診 | 状態ごとに区切った一覧。検索、詳細、登録、編集 |
| 社員の詳細 | 状況の内訳、最優先の1件、資格の一覧、次回予定日、実施の記録 |
| 資格・講習・健診の詳細 | 受講・実施の履歴、回ごとの控え、根拠となる法令、次にやること |
| 道具・機器の点検 | 上の3つと同じ構成。絶縁用保護具、測定機器、高所作業車、社用車 |
| 安全書類の提出前チェック | 提出日を入れて、その日に書類を止めるものを洗い出す |
| 種類の設定 | 種類・周期・警告日数の確認と変更 |
| AIサポート | 台帳への質問に答え、操作の場所を画面上で光らせる |

**既定で無効にしている機能**（フラグ 1 つで開きます）

| 機能 | フラグ | 状態 |
|---|---|---|
| 控えの画像を預かる | `ATTACHMENTS_ENABLED` | 構造・画面ともに実装済み。保存は未実装 |
| 証の写真から期限を読み取る | `PHOTO_READING_ENABLED` | 画面と読み取り役の差し替え口を実装。既定はモック |
| 外部の AI に言い換えを頼む | `AI_API_ENABLED` | 実装済みだが **未検証**（下記） |

修了証には氏名・生年月日・証番号が写ります。社員の画面からは期限の判定に使わない
個人情報を意図的に外しているので、同じものを画像として入れ直さないよう、
誰でも触れる状態では受け付けない設定にしています。

**未検証の経路**：`core/intent_llm.py` と `core/certificate_reader.py` の
`ClaudeCertificateReader` は、API キーが無いため実際に呼び出して動くことを
確認していません。書いてあるだけで、動作は保証しません。コード内にも明記しています。

## 3. 画面の決まりごと

利用者に PC へ不慣れな人が含まれる前提で決めました。

**折りたたまない。** アコーディオンや展開ボタンを使いません。
隠れている機能は、その存在を知らない人にとっては無いのと同じだからです。
押す先はすべて最初から見えています。

**状態を色だけで表さない。** 色の隣に必ず言葉を置きます
（🔴 期限切れ／⚪ 日付未入力／🟠 期限間近）。

**危険なものほど上・左に来る。** 並びは 期限切れ → 日付未入力 → 資格情報なし → 期限間近。
日付未入力を期限間近より上に置くのは、**未入力は書類を止めるが、
期限間近はまだ止めない**ためです。

**記録が1件も無い対象を「問題なし」にしない。** 登録しただけの社員や、
買ったばかりの道具は「資格情報なし（点検情報なし）」として扱います。
問題が無いのではなく、何も分かっていないだけだからです。

**検索は絞り込みを飛び越える。** 「対応が必要な人だけ」を表示していても、
名前を打てば全員から探します。打ったのに出てこない状態を作らないためです。

**まだ作っていない操作は、押せる状態で置かない。** 無効にして理由を書きます。
押しても何も起きないボタンは、無いより悪いためです。

## 4. 設計上の判断

**(1) 前回実施日を保持しない**

`Holding.last_done_on` は実施記録の集合から導出します。
同じ事実を二箇所に持つと、片方だけ更新されたときに静かに食い違うためです。

**(2) 期日が決められないときは推測しない**

前回実施日が無い、周期が登録されていない。そうした場合は `None` を返し、
状態を「未確定」とします。登録日から起算したり、今日で補ったりはしません。

**分からないものを「まだ大丈夫」と表示することが、この種の台帳では最も危険**だからです。
提出前チェックでは、未確定の行も通しません。

一方、免状のように**そもそも期限を持たない種類**は、未確定として警告に混ぜません。
期限のないものを期限として並べると、台帳そのものの信頼が落ちます。

**(3) 周期をコードに書き込まない**

種類・周期・警告日数はすべてデータ側にあり、画面から変更できます。
実際の周期は設備の条件や社内規程で変わるもので、外部が決め打ちできません。

同じ理由で、監理技術者講習の有効期限は計算していません。
この講習の有効期間は「受講日の翌年1月1日から5年後の12月31日まで」という
特殊な数え方ですが、**正本は修了証に印字された期限**です。
正本があるものを計算し直して食い違わせる意味はないので、証面の期限を登録します。
車検も同じ理由で、車検証の満了日をそのまま登録します。

**(4) 不変条件はデータを持っている側で守る**

「期限間近」の日数が「予告」の日数を追い越すと例外になります。
当初は画面側でそろえていましたが、呼び出す側に決まりを持たせると、
呼ぶ場所が増えたときに揃え忘れます。`Ledger.set_soon_days` に移しました。

**(5) 月末は繰り上げずクランプする**

1月31日の1か月後は3月3日ではなく2月28日。うるう年も同様に扱います。
点検や講習の周期は「何か月後」で定められることが多く、日数加算では月ごとにずれます。

**(6) 道具は管理番号で特定する**

「絶縁手袋」は何組もあります。名前だけでは現物にたどり着けないため、
管理番号と型番を持たせ、検索でも引けるようにしています。

**(7) AIサポートは答えを台帳の関数から作る**

文章を組み立てて返すのではなく、`build_rows` や `submission_check` の結果を
そのまま言葉にします。独自に文章を生成すると、画面が「3件」と言っているのに
「4件」と答える、という食い違いが起きます。同じ関数から作れば食い違いようがありません。

答えられない聞き方には、**近いものを推測せずに「答えられません」と言います。**
台帳の表示と食い違う答えを出すのが、この道具では一番困るためです。

書き込みは一切しません。読むだけ、指すだけです。操作の場所は画面上で光らせますが、
押すのは人です。

外部の AI に接続する場合も、頼むのは**言い換えだけ**です
（「来月あたま出す書類で引っかかりそうなのある？」→「2026年10月1日に提出したら
何が引っかかる？」）。答えの数字と名前は台帳から出します。
言い換え役が数字を含む文を返しても、それが答えにならないことをテストで確かめています。

**(8) 写真から読み取れなかった項目は空欄のままにする**

日付が読めなかったときに「たぶんこれだろう」を入れると、人は埋まっている欄を
そのまま通してしまい、目視確認が形だけになります。空欄なら気づきます。
読み取った値もそのままは保存せず、必ず人が確定させます。

**(9) 消すときは、何が一緒に消えるかを見せてから消す**

対象を消すと、その記録もすべて消えます。押した直後には消さず、
「登録されている項目 3件／実施・点検の記録 3件」と数えて見せてから確認します。

## 5. 動かし方

```bash
pip install -r requirements.txt
streamlit run app.py
```

テスト:

```bash
pip install -r requirements-dev.txt
pytest
```

README に載せている数字を計算し直す:

```bash
python -m data.stats
```

同梱データを作り直す（実行した日を基準に組み直されます）:

```bash
python data/generate_seed.py
```

## 6. 検証結果

このリポジトリの状態で実測した結果です。

| 検証 | 結果 |
|---|---|
| テスト `pytest` | 157 ケース 成功 |
| 同梱データの整合 | 参照切れ 0（テストで検証） |
| 外部通信 | なし |
| 依存パッケージ | streamlit のみ |

テストは境界値と、**間違えたときに安全側へ倒れないケース**を重点的に確認しています。

- 月末クランプ、うるう年、年跨ぎ
- しきい値ちょうどの日を含むか
- 期日未確定を「余裕あり」に変えていないか
- 未来日を実施日として受け付けていないか（受け付けると超過が隠れる）
- 資格者証が有効でも講習が切れていれば配置できないこと
- 記録漏れを後から入力しても、最新の実施日が正本であり続けること
- 状態と期日を別々の資格から拾って矛盾したカードを作っていないか
- 記録が1件も無い対象を「問題なし」にしていないか
- 行の検査だけでは、記録が無い対象を見逃すこと（別の関数で補っている）
- 基準日より後の実施記録を、その基準日の判定に使っていないこと
- 期限が無いことと、期限が分かっていないことを混ぜていないこと
- 保存データに知らない区分値が入っていたら、読み込みで止めること
- 画面が実際に立ち上がり、主要な導線が例外なく通ること

### 外部レビューで見つかり、直したもの

一度、別のAIに全コードを渡して指摘を出させ、**一件ずつ手元で再現してから**直しました。
指摘をそのまま受け入れてはいません（過去に、この分野の事実関係を誤った指摘を
繰り返し受けたことがあるためです）。再現できたものだけを直しています。

| 指摘 | 何が起きていたか | 直し方 |
|---|---|---|
| 基準日より後の実施記録を使っていた | 2025年6月時点の判定に2026年1月の受講を使い、期日が1年先にずれていた | `latest_done` に基準日を渡し、その日までの記録だけを見る |
| 有効期限型の資格を更新できなかった | 免状を更新しても、台帳の期限を書き換える経路が無かった | 詳細画面に新しい有効期限の登録欄を追加 |
| 「期限なし」と「期限が不明」が同じ状態だった | 有効期限のない免状が「未確定」に混ざり、本当に日付が無い行が埋もれていた | `no_deadline` を独立した状態として分離 |
| AIが年の無い日付を勝手に補っていた | 「8月1日」を今年と決めつけ、提出日を1年ずらして判定していた | 補わずに年を聞き返す |
| 内部IDが連番で、同姓同名を区別できなかった | 同じ名前の社員がいると、片方の記録がもう片方に混ざりうる | UUIDに変更し、選択・集計もIDで行う |
| 保存データを検証していなかった | 知らない区分値が入ると、期限のある資格が「期限なし」として静かに扱われる | 読み込み時に検査して止める |
| 拠点が登録済みの社員から数え上げだった | その拠点の最後の1人を消すと、拠点ごと選択肢から消えて登録できなくなる | 拠点・職種を台帳が持つ一覧として独立させた |
| 実装より古い案内文が残っていた | 登録画面はあるのに「まだ作っていません」と表示していた | その場で登録へ進めるボタンに置き換え |
| README の数字がずれていた | 「1年後 50件」と書いてあったが、実測は117件だった | `data/stats.py` で計算し、テストで突き合わせる |

**指摘のうち、直さなかったものもあります。** 台帳の永続化（現状はセッション内のみ）と
控え画像の保存先は、置き場所を決める話であって、動かす環境が決まってから判断すべきものです。

## 7. データについて

**同梱データはすべて架空です。** 社員名・道具名・保管場所は実在の個人・顧客とは
関係ありません。`data/generate_seed.py` で生成しており、乱数は使っていません。

規模は 社員76名／道具・機器36件／種類21／保有130件。

種類の周期は、次の公開情報を参考にした**例示**です。
実際の周期は設備・契約・社内規程により異なるため、「種類の設定」で変更できます。

- 監理技術者資格者証／監理技術者講習 — 建設業法および同施行規則
  （令和3年1月1日改正で講習の有効期間の数え方が変更）
- 第一種電気工事士 定期講習 — 電気工事士法
- 危険物取扱者 保安講習 — 消防法
- 定期健康診断 — 労働安全衛生法
- 絶縁用保護具・防具の定期自主検査（6か月以内ごと） — 労働安全衛生規則 第351条
- 特定自主検査（1年以内ごと） — 労働安全衛生法
- 自家用電気工作物の月次・年次点検 — 電気事業法
- 測定機器の校正、内部監査 — ISO 9001:2015
- 自動車の継続検査 — 道路運送車両法

**有効期限が存在しない資格**（電気主任技術者の免状、第一種電気工事士の免状、
技能講習の修了証、特別教育など）は、保有の記録として登録しますが、
期限としては扱いません。

## 8. 構成

```
app.py              画面（Streamlit）。計算は持たない
core/
  schedule.py       期日の計算。外部依存なしの純粋関数
  models.py         データの型と保存形式の相互変換
  review.py         判定。すべて基準日を引数で受ける
  store.py          読み書き
  assistant.py      AIサポートの判定。Streamlit を import しない
  intent_llm.py     外部の AI に言い換えだけを頼む（未検証）
  certificate_reader.py  証の画像から日付を読み取る（既定はモック）
ui.py               配色と部品（ピル・タイル・見出し）。計算は持たない
data/
  requirements.json 種類マスタ
  seed.json         同梱データ（生成物・架空）
  generate_seed.py  同梱データの生成
  stats.py          README に載せる数字の計算
tests/              pytest
```

本体は Python 12ファイル・4,607行、テストが 10ファイル・1,542行です。HTML・CSS・JavaScript のファイルは持たず、
見た目の調整は `ui.py` の中に CSS としてまとめています。

画面はドメイン層の薄い皮で、期日の決め方と判定はすべて `core/` にあります。
**`core/` は Streamlit を import しません。**
テストの大半は `core/` に対するもので、画面を通さずに検証しています。
画面については `streamlit.testing` で実際に起動し、主要な導線が例外なく
通ることを確かめています（`tests/test_app_smoke.py`）。

構文だけを見るテストでは足りません。実際、構文が正しいまま実行時に落ちる状態で
「テスト成功」と表示させてしまったことがあり、それが起動テストを足した理由です。
